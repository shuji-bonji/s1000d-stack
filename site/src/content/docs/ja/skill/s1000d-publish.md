`s1000d-publish` は、構造化した下書きから S1000D® のデータモジュールを 1 件ずつ作り、検証を通して CSDB に入れる Skill です。体験型マニュアルを経由しない、技術文書の書き手のための手順です。CSDB にある手順・説明のデータモジュールに、手順・段落・警告・リストの項目を足す・取り除く・移す依頼も扱います。発行済みの版から作業中の版を始めて、変更の印と更新の理由を付ける手順も持ちます。Skill は、どの MCP サーバーをどの順番で呼び、各段階で利用者に何を聞くかを Claude に伝えるもので、組み立てや検証の処理は持ちません。

[GitHub](https://github.com/shuji-bonji/s1000d-publish-skill) / [Release](https://github.com/shuji-bonji/s1000d-publish-skill/releases)

## 何をする Skill か

- **渡すもの**: 材料（文章、メモ、既存のデータモジュール）、出力先の CSDB のフォルダー、機密区分、採番の規則です。データモジュールの種類（説明、手順、プロセス、故障探求）は、利用者と相談して決めます。
- **受け取るもの**: 検証したデータモジュール 1 件、作ったデータモジュールが DML（データ管理リスト）に載っているかの照合結果、Publish Report（検証状態、自動で直した修正、書き込んだファイル）です。書き込みは、利用者が確認した後に行います。

## 前提の MCP サーバー

| MCP サーバー | 必須・任意 | 最低版 | 役割 |
| --- | --- | --- | --- |
| [s1000d-writer-mcp](/s1000d-stack/ja/mcp/writer-mcp/) | 必須 | 0.6.0 | 下書きからデータモジュールを組み立てて検証し（`build_data_module`）、選んだ修正を適用します（`apply_fixes`）。CSDB にあるデータモジュールの構造を編集し（`edit_data_module`）、作業中の版を始め（`start_revision`）、更新の理由を足します（`add_reason_for_update`） |
| [s1000d-verify-mcp](/s1000d-stack/ja/mcp/verify-mcp/) | 必須 | 0.6.1 | 書いたデータモジュールを検証し（`verify_data_module`）、DML と照合します（`reconcile_dml`） |
| [s1000d-brex-mcp](/s1000d-stack/ja/mcp/brex-mcp/) | 任意 | 0.4.0 | プロジェクトの BREX の決まりを、書き手向けに説明します（`explain_brex`） |
| [s1000d-reader-mcp](/s1000d-stack/ja/mcp/reader-mcp/) | 任意 | 0.13.0 | CSDB にあるデータモジュールの題名・版・参照先を確かめます（`read_data_module`）。読んだ本文から作り直すことには使いません。`edit_data_module` の手順では、編集する場所を得るために必要です |

必須のサーバーが接続されていないとき、Skill は作業を始めず、接続の方法を伝えて止まります。任意のサーバーが接続されていないときは、報告の該当項目に「未実施（ツール未接続）」と書きます。

## 手順の流れ

```mermaid
flowchart LR
  A["材料と種類を<br/>利用者と決める"] --> B["プロジェクトの BREX の<br/>決まりを要約する"]
  B --> C["下書きを作り<br/>利用者が確認する"]
  C --> D["書き込まずに<br/>組み立てて検証する"]
  D --> E["残った修正を<br/>利用者が選ぶ"]
  E --> F["確認後に書き込み<br/>検証する"]
  F --> G["DML と照合する"]
  G --> H["Publish Report"]
```

1. 材料、新規か版を上げるのか、出力先の CSDB のフォルダー、機密区分を確かめ、データモジュールの種類を利用者と決めます。
2. brex サーバーが接続されていれば、プロジェクトの BREX の決まりを、書き手向けに要約します。応答にない決まりは足しません。
3. 採番の規則を聞きます。情報コードの既定はないので、プロジェクトが登録したコードを聞きます。
4. 題名・段落・手順・警告・表・参照だけからなる下書きを作り、利用者に見せて確認してもらいます。DMC や BREX の参照は書きません。
5. 書き込まずに組み立てて検証します。残った修正のうち、候補が複数あるものは利用者が選び、候補がないものは利用者に聞きます。
6. 利用者が書き込み先を確認してから書き込み、書いたデータモジュールを検証します。
7. DML と照合し、作ったデータモジュールが DML に載っているかを報告します。載っていないときは、利用者に伝えます。
8. 作った結果と検証状態を Publish Report にまとめます。

## CSDB にあるデータモジュールの構造を変える

CSDB にある手順・説明のデータモジュールに、手順・段落・警告（注意・注記）・リストの項目を足す・取り除く・移す依頼は、writer サーバーの `edit_data_module` で行います。データモジュールを読んで下書きから作り直すことはしません。作り直すと、下書きに書けない要素と属性が無くなるためです。`edit_data_module` は、元の XML の編集した範囲だけを書き換えます。

発行済みの版を S1000D の版の決まりに沿って直すときは、writer サーバーの `start_revision` で作業中の版を始め、`edit_data_module` の `marking` で変更の印を付けます（0.4.0 から）。

```mermaid
flowchart LR
  A["何を変えるかと<br/>版を確かめる"] --> R["発行済みの版なら<br/>作業中の版を始める"]
  R --> M["変更の印を付けるかを<br/>利用者に聞く"]
  M --> B["reader で<br/>場所を得る"]
  B --> C["編集を組む"]
  C --> D["書き込まずに呼び<br/>結果を読む"]
  D --> E["利用者が<br/>確認する"]
  E --> F["書き込み<br/>検証する"]
```

1. どのデータモジュールの、どこに、何をするのかを確かめ、版（`issueInfo`）を見ます。発行済みの版（`inWork` が `00`）は、そのままでは編集できません。「作業中の版を始めて、S1000D の決まりに沿って直す」「版を変えずに書き換える（試作・練習）」「やめる」の 3 つから、利用者に選んでもらいます。
2. 作業中の版を始めるときは、`issueType`（`changed`・`revised`・`status`）を利用者に聞き、writer サーバーの `start_revision` を呼びます。作業中の版は新しいファイルとして書かれ、発行済みの版のファイルは変わりません。これ以降は、新しいファイルを対象にします。
3. 作業中の版を編集するときは、変更の種類を利用者に聞きます。変更の印で示す変更では、更新の理由の文、`updateReasonType`、`changeMark` も聞きます。編集上の変更（`urt01`）には、変更の印を付けません。
4. reader サーバーの `read_data_module` を `includeLocation: true` で呼び、節点の `location.path` を写します。手順の文（手順の節点の `text` にまとめて返る段落）だけを取り除く・移すときは、手順の節点の `textLocations` にある場所を写します。場所を自分で組み立てません。
5. 編集（`insert`・`remove`・`move`）を組みます。足す節点は下書きの節点で、XML は書きません。利用者が示していない `id` は付けません。変更の印を付けるときは、`marking` を添えます。その理由による最初の編集は `marking.reason`、同じ理由による 2 回目からの編集は `marking.reasonRefId` です。
6. 書き込まずに呼びます。断られた編集（`refusals[]`）は、理由ごとに対処します。編集で XSD のエラーが増えたとき（`newSchemaErrors[]`）は、位置か編集を変えて呼び直します。取り除いた `id` をほかのデータモジュールが指しているとき（`referencedFromOtherObjects[]`）は、利用者に聞きます。
7. 変わる場所と検証状態を示して、利用者の確認を得ます。変更の印を付けるときは、どの要素にどの印が付くかと、足される更新の理由も示します。付けないときは、版と変更の印を変えていないことを示します。
8. 書き込み、verify サーバーで検証して報告します。報告には、発行はしていないことを書きます。
9. 変更の印を付けない変更の理由（編集上の変更の理由、`issueType` が `revised`・`status` の版の理由）は、writer サーバーの `add_reason_for_update` で足します。

次の依頼は、まだ扱えません。できないと伝えます。

- 表・図・前提条件の品目を足す・取り除く・移すこと
- 段落の文を書き換えること
- 発行（`inWork` を `00` に戻し、発行番号を上げること）と、発行日・品質保証の状態の更新
- 文の一部への変更の印（`changeInline`）と、表・図への変更の印

節点を別の内容に置き換える依頼は、変更の印を付けるときだけ扱えます。同じ呼び出しで、元の節点を取り除く編集と、その隣に新しい節点を足す編集を渡します。元の節点は `delete` の印で残ります。

## Skill がしないこと

- XML を書きません。書くのは下書きだけで、XML は writer サーバーが組み立てます。
- 情報コード、機密区分、適用性を、利用者に聞かずに決めません。
- 候補の外の値で修正しません。
- BREX の決まりを、サーバーの応答にない内容で説明しません。
- DML を作ったり更新したりしません。writer サーバーにその機能がまだないので、載っていないときは、利用者のツールで追記してもらいます。
- `schema-not-found` と `not-run` を合格とは書きません。S1000D への準拠は判定しません。
- 利用者が明示していないのに、発行済みの版を書き換えません（`allowReleasedIssue: true` を自分の判断で渡しません）。
- 利用者に聞かずに、作業中の版を始めません。`issueType`・更新の理由の文・`updateReasonType`・`changeMark` も、自分で決めません。
- 「発行した」「版を上げた」とは報告しません。行うのは、作業中の版を始めることだけで、発行番号は上がりません。`marking` を渡していないのに、「変更の印を付けた」とも報告しません。

## 入れ方

Claude Code では、次のコマンドで入れます。

```text
/plugin install s1000d-publish@shuji-bonji
```

必須の MCP サーバーは、Skill の `plugin.json` に依存として宣言してあります。MCP サーバーの設定（`S1000D_SPEC_DIR` など）は[導入手順](/s1000d-stack/ja/guide/getting-started/)にあります。
