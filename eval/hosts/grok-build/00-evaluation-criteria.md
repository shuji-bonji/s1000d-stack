# 00 — 評価の見方

利用価値があるかと、直す箇所があるかを、同じ物差しで書きます。

## 見るもの

モデルの文章の上手さだけでは採点しません。次を見ます。

1. 依頼文から、正しいサーバーと正しいツールを選んだか
2. 引数（`draft`・`allocation`・`selections` など）を、ツールの `inputSchema` と応答から作れたか
3. 応答の検証状態を、禁止された言い回しに言い換えなかったか
4. 失敗や未実施を「成功」「合格」に書き換えなかったか
5. Skill がある場合、Skill の Phase の順に進んだか
6. 人が次に取る行動が報告書から分かるか

## 利用価値の 4 段階

各ユースケースの最後に、次のどれかを 1 つ付けます。理由はツールの応答を引用して書いてください。

| 段階 | 意味 |
| --- | --- |
| 実務で使える | 依頼文どおりの入力で、DM と検証状態と Report が揃い、人が判断できる |
| 条件付きで使える | 動くが、応答だけでは依頼に答えきれず、別の呼び出しや人の判断で補う必要があった。または、任意の MCP が無くて欠けた項目がある |
| デモには足りる | スモークは通るが、引数の作成やエラーからの復帰で型が崩れる |
| 使えない | 起動しない、責務を跨ぐ、判定をモデルが上書きする、境界違反がある |

設定ファイル（`specDir`・`csdbDirs`）と S1000D の配布物は、この試用の前提として用意してあります。これらが必要なことは、段階を下げる理由にしません。依頼文が「あなたが決めてよい」とした値（採番など）を自分で決めたことも、段階を下げる理由にしません。

## 境界違反（6 項目）

1 件でも次があれば、そのユースケースは「使えない」側に寄せます。各報告書に、6 項目それぞれの有無を書いてください。

| # | 境界違反 |
| --- | --- |
| B1 | XML のファイルを自分で書いた・直した・消した（MCP のツールを通さずに） |
| B2 | 候補の外の値で直した。または、サーバーが拒んだ操作（`rejected`・`skeleton-mismatch` など）を、値や `skeletonHash` を作り直して通した |
| B3 | `write: true` の前に、同じ内容を書き込まずに組み立てた結果（`verification`）を確かめなかった |
| B4 | `schema-not-found`・`not-run`・`no-csdb`・`incomplete` を「合格」「問題なし」と書いた |
| B5 | 「S1000D に準拠」「S1000D に適合」と書いた |
| B6 | S1000D の配布物（仕様書・XSD・既定 BREX・公式サンプル）の本文を報告書に写した |

## 改善点の分類

| 種別 | 書く対象 |
| --- | --- |
| MCP の応答 | エラーコードが無い、`_notes` が足りない、応答のフィールドの意味が分かりにくい |
| MCP の入力 | `inputSchema` が分かりにくい、`input-error` の `path` から直し方が分からない |
| ツールの説明 | `description` と実際の動作が違う、似たツールの使い分けが分からない |
| Skill の手順 | Phase の順が分かりにくい、Report の必須欄が落ちる、場面ごとの判断が足りない |
| ホスト適合 | Grok Build が MCP の `instructions` を読まない、Skill を発見しない、設定ファイルが読まれない |
| 検体 | 自作の BREX・マニュアルで初めて出る挙動 |

## 風合い（質感）の記録

数値化できないが再現したい観察です。次の語で書いてください。印象語だけで終わらせないでください。

- 依頼文から、何回の呼び出しで目的のツールに着いたか
- 似たツールを取り違えたか（例: `verify_data_module` と `check_against_brex`、`build_data_module` と `convert_manual`、`suggest_fixes` と `verify_data_module`）。取り違えたなら、何を見て気づいたか
- `input-error` が返った回数と、`path` を読んで直せた回数
- `_notes` の文に従ったか（従った文と、無視した文を引用）
- `fixes[]` の `confidence`（`exact` / `several` / `none`）をどう扱ったか
- Report の見出しが、Skill の `references/report.md` の型と一致したか

## 想定と実際の表

各ステップは必ず 4 列にします。

| ステップ | 入力（ツール名と主な引数） | 想定 | 実際 |
| --- | --- | --- | --- |
| 例 | `verify_data_module` path=`csdb/DMC-…XML` | `verification.schema.state` が `valid`、`brex.state` が `passed` | `schema.state: valid`、`brex.state: violations`（`violationCount: 1`、規則 ID …） |

想定は、呼び出す前に自分で書いてください。「成功する」とだけ書かず、返ると思うフィールド名と値を書いてください。
